# 用户建议与 NPC 主体性 v1 开发基准

## 核心原则

用户可以向 NPC 提建议，但建议不是命令。NPC 必须根据自己的状态、性格、关系、现有计划和稳定规则，独立产生以下结果之一：

- `accepted`：建议与当前需要一致，转化为 NPC 自己的意图。
- `adjusted`：认可方向，但修改为自己的节奏，执行时间晚于直接接受。
- `deferred`：当前已有计划，先保留建议，之后重新判断。
- `declined`：建议与当前需要或边界冲突，不生成意图。

## 受控建议类型

建议类型来自 `characters/presets.yaml` 中每个 `intention_templates[].suggestion_type`：

- `rest`：休息恢复；
- `walk`：散步与压力调节；
- `connect`：主动联系某个关系人物；
- `project`：继续兴趣项目；
- `explore`：探索新事物。

客户端可以附带最多 500 字说明，但说明只作为用户原话保存，不参与事件模板渲染，也不会成为执行参数。这样可以防止自然语言绕过配置边界。

## 决策评分

评分综合：

- 建议对应的状态需求是否已经出现；
- 相关人格权重；
- NPC 对 UNA 的熟悉、好感和信任；
- 独立性形成的自主边界成本；
- 按用户、人物、日期和模板计算的稳定扰动。

完整分数和分项证据写入 `evaluation_json`，只用于测试、调试和后续调参，不由客户端 API 返回。

## 持久化

`ai_actor_suggestions` 保存建议请求、NPC 决策、回应、可选目标、关联意图、延后重评时间及幂等键。

客户端必须提供 `request_id`。幂等键由用户、NPC、请求 ID 和规则版本组成；重复请求返回第一次决策，不会重复创建意图。

接受或调整建议时，系统创建普通 `ai_actor_intentions`：

- `decision_context.source_kind = user_suggestion`；
- 保留来源建议 ID；
- NPC 自己的模板决定摘要、行动、状态和关系变化；
- 用户原话不会写进结果事件。

## 延后重评

人物已有活跃意图时，建议进入 `deferred`，默认 24 小时后可重评。离线结算顺序为：

1. 固定生活和共同互动；
2. 重评到期建议；
3. 处理或形成 NPC 意图。

如果人物重评时仍有活跃计划，建议继续保留；空闲后才可能接受、调整或拒绝。

## API 与隐私

- `POST /api/life/actors/{actor_id}/suggestions`：提交受控建议。
- `GET /api/life/actors/{actor_id}/suggestions`：查询建议及 NPC 回应。

公开响应包含建议类别、用户原话、决策状态、原因代码、NPC 回应和关联意图 ID，但不包含内部评分明细。

聊天上下文只注入 NPC 的安全回应，并明确要求模型不要把建议描述为命令，不公开内部评分。

## v1 边界

- v1 暂不从任意聊天文本自动抽取建议，避免误把普通对话识别为命令。
- `connect` 可以指定已启用人物；未指定时默认建议联系 UNA。
- 非关系类建议禁止携带目标人物。
- 用户不能选择执行文案、关系增量、公开程度或状态增量。
- 前端建议入口与调试界面可在后续阶段建立在本 API 上。
