# P1：AI 自由驱动 Live2D 与即时用户动作设计

> 日期：2026-07-27
>
> 状态：设计已实施；2026-07-29 已按 post-update 架构完成渲染顺序修正与验证
>
> 实施隔离：仅在 `codex/p1-live2d-motion-v3` 分支及其 worktree 中工作；未经用户明确要求，不合并到 `main`

## 一、背景

当前项目已经完成 P0 稳定性修复，并具备以下基础：

- 大模型控制文本不会进入字幕、语音、历史记录和记忆；
- 后端通过 WebSocket 独立发送 `live2d_action_v2`；
- 前端能够根据 8 种语义意图生成程序化动作；
- 用户发送消息后会立即触发轻微倾听反应；
- 动作采样器异常不会再终止整个 Live2D ticker；
- 语音口型保持独立控制权。

现有实现仍属于“8 种意图映射到固定配方”的过渡方案。它不能让 AI 直接决定连续动作轨迹，也没有读取当前模型的真实参数范围，更没有一个统一的状态混合器。P1 要在保留 P0 安全边界的前提下完成这些能力。

本次新增需求是：当用户明确要求“上下点头三次”“慢慢摇头”等动作时，模型必须在用户点击发送后立即执行，不等待 AI 开始回复。

## 二、目标

P1 需要实现：

1. 用户明确动作指令的本地即时识别和执行；
2. AI 输出与模型无关的连续动作通道和稀疏关键帧；
3. 前端根据当前 Live2D 模型的真实参数能力进行映射和限幅；
4. 单一 `Live2DStateMixer` 统一仲裁待机、微反应、AI 动作、用户指令、眨眼和口型；
5. 动作之间能够平滑叠加、抢占、中断和恢复；
6. 任意非法数据或单通道异常都不能让 Live2D 停止渲染；
7. 保留 `live2d_action_v2` 作为旧消息和异常情况的兼容兜底；
8. panda_cake 与 Hiyori 两个现有模型均可安全工作。

## 三、不在本次范围内

- 不允许 AI 直接输出 `ParamAngleX`、`Param159` 等模型原始参数 ID；
- 不允许动作协议控制嘴部开合和嘴型；
- 不直接写入头发、衣服等由 Live2D Physics 负责的参数；
- 不新增动作编辑器界面；
- 不保存或跨设备同步瞬时动作播放进度；
- 不制作、调用或新增固定 `.motion3.json` 动作文件；
- 不在本次工作中调整聊天、账号、朋友圈或记忆系统。

## 四、方案选择

采用“双阶段混合驱动”：

### 4.1 第一阶段：用户指令即时动作

前端在用户点击发送时同步检查原始文字。识别到高置信度动作指令后，直接生成归一化动作计划并送入本地混合器，与消息网络请求并行执行。

该路径不调用额外模型，不等待后端，不增加 AI 首字延迟。目标是在消息发送后的 1～2 个渲染帧内开始动作。

### 4.2 第二阶段：AI 上下文表演

AI 回复仍通过现有控制前缀输出动作数据。AI 负责决定动作通道、关键节点、幅度、节奏和表演性，前端负责插值、缓动、小范围确定性变化、模型适配和安全限幅。

用户指令正在占用的通道不会被普通 AI 动作覆盖；AI 仍可控制其他未冲突通道。

## 五、总体架构

### 5.1 `ImmediateGestureParser`

职责：

- 识别用户明确要求的动作；
- 提取动作类型、次数、速度、幅度、并行和先后关系；
- 识别否定表达；
- 只有达到高置信度时才返回结构化结果。

它不生成 Live2D 参数，也不依赖模型。

首批支持：

- 点头、摇头；
- 抬头、低头、向左看、向右看；
- 左右歪头；
- 身体前倾、后退、左右倾斜；
- 眨眼、闭眼；
- “点头并眨眼”等简单并行动作；
- “先点头两次，再摇头”等简单顺序动作；
- 1～5 次数量；
- “轻轻、明显、用力”等幅度修饰；
- “慢慢、快速”等速度修饰。

“不要点头”“不是让你摇头”等否定句不得触发动作。无法可靠识别的复杂表达不执行本地动作，交给 AI 回复阶段处理。

### 5.2 `ParametricGestureGenerator`

职责：

- 把解析结果转换成 `MotionPlanV3`；
- 通过连续数学曲线生成关键帧，而不是选择固定动作文件；
- 根据次数、速度、幅度和随机种子生成轻微变化；
- 保证起点和终点平滑回到中性位置。

例如“点头三次”由三组动态 `head_pitch` 波形组成。每次的幅度和节奏可以有小范围变化，但次数必须准确。

### 5.3 `MotionPlanV3`

即时用户动作和 AI 动作共用同一种前端内部结构。后端发送的事件类型为 `live2d_motion_v3`。

```json
{
  "type": "live2d_motion_v3",
  "motion_id": "唯一动作ID",
  "source": "user_command",
  "created_at_ms": 1785124800000,
  "expires_at_ms": 1785124806800,
  "duration_ms": 1800,
  "variation_seed": 38124,
  "blend": {
    "in_ms": 100,
    "out_ms": 180
  },
  "tracks": [
    {
      "channel": "head_pitch",
      "mode": "override",
      "keyframes": [
        { "t": 0.0, "value": 0.0, "easing": "ease_in_out" },
        { "t": 0.12, "value": -0.55, "easing": "ease_in_out" },
        { "t": 0.25, "value": 0.2, "easing": "ease_in_out" },
        { "t": 1.0, "value": 0.0, "easing": "ease_in_out" }
      ]
    }
  ]
}
```

协议约束：

- `motion_id` 必须是非空字符串，并用于 WebSocket 和前端播放去重；
- `source` 只接受 `user_command`、`ai_reply`、`local_micro_reaction` 和 `legacy_fallback`；
- AI 只提供动作内容；后端必须覆盖 AI 自报的 `type`、`motion_id`、`source`、`created_at_ms` 和 `expires_at_ms`；
- 本地即时动作的权威字段由前端生成，AI 动作的权威字段由后端生成；
- 前端收到 `expires_at_ms` 已过期的网络动作时直接丢弃，不补播旧动作；
- `duration_ms`：用户动作 200～5000 毫秒，AI 动作 400～4000 毫秒；
- 每个动作最多 8 条轨道；
- 每条轨道最多 12 个关键帧；
- `t` 必须按升序排列且位于 `0～1`；
- `value` 必须是有限数值且位于 `-1～1`；
- `mode` 只接受 `override` 或 `additive`；
- `easing` 首批只接受 `linear`、`ease_in`、`ease_out`、`ease_in_out`；
- 禁止未知字段改变执行语义；
- 单条非法轨道可以被丢弃；没有任何合法轨道时整条动作失效。

### 5.4 `ModelCapabilityMap`

职责：

- 在模型加载完成后读取真实参数 ID、最小值、最大值和默认值；
- 把语义通道映射到当前模型实际参数；
- 标记嘴部、物理参数等保留参数；
- 提供归一化值到模型值的转换和最终限幅。

当前 `pixi-live2d-display 0.4.0` 的 Cubism4 CoreModel 没有公开的 `getParameterId(index)`。实现不得再次假设该 API 存在。

参数能力读取顺序：

1. 受保护地读取包装器已有的 `_parameterIds`；
2. 若不存在，则读取 `coreModel._model?.parameters?.ids`；
3. ID 数组仍不可用时，使用当前模型 CDI 元数据和标准参数别名表作为降级来源；
4. 范围和默认值通过真实存在的按索引 API 读取：
   - `getParameterMinimumValue(index)`；
   - `getParameterMaximumValue(index)`；
   - `getParameterDefaultValue(index)`。

任何私有字段访问都必须有结构检查和异常隔离。读取失败时返回部分能力表，不得影响模型显示。

### 5.5 `Live2DStateMixer`

职责：

- 持有活动动作和通道所有权；
- 每帧采样全部输入层；
- 按通道进行叠加或覆盖；
- 处理淡入、淡出、中断、过期和恢复；
- 输出经过能力映射与限幅的最终参数值。

现有 `useLive2DController.js` 不再自行拼接多个来源的参数。它只负责：

1. 维护渲染生命周期；
2. 将新动作送入混合器；
3. 每帧取得混合结果；
4. 安全写入 CoreModel。

### 5.6 后端 `MotionDirectorV3`

职责：

- 校验不可信的 AI 动作结构；
- 拒绝未知通道、嘴部通道、非法数值和非法时间；
- 应用时长、轨道数和关键帧数限制；
- 控制动作频率和表演强度；
- 生成服务端 `motion_id`、创建时间和过期时间；
- 通过现有用户级 WebSocket 发送 `live2d_motion_v3`；
- 在 v3 无效时按策略降级到 `live2d_action_v2`。

## 六、语义通道

P1 首批允许 AI 和即时动作使用：

| 语义通道 | 含义 | 常见模型参数 |
| --- | --- | --- |
| `head_yaw` | 左右转头 | `ParamAngleX` |
| `head_pitch` | 抬头、低头、点头 | `ParamAngleY` |
| `head_roll` | 左右歪头 | `ParamAngleZ` |
| `body_yaw` | 身体左右转向 | `ParamBodyAngleX` |
| `body_pitch` | 身体前倾、后退 | `ParamBodyAngleY` |
| `body_roll` | 身体左右倾斜 | `ParamBodyAngleZ` |
| `gaze_x` | 眼球左右 | `ParamEyeBallX` |
| `gaze_y` | 眼球上下 | `ParamEyeBallY` |
| `eye_open` | 眼睛开闭 | `ParamEyeLOpen`、`ParamEyeROpen` |
| `eye_smile` | 笑眼 | `ParamEyeLSmile`、`ParamEyeRSmile` |
| `brow_y` | 眉毛上下 | `ParamBrowLY`、`ParamBrowRY` |
| `brow_form` | 眉毛形状 | `ParamBrowLForm`、`ParamBrowRForm` |
| `cheek` | 脸红程度 | `ParamCheek` 或模型适配参数 |

`mouth_open`、`mouth_form`、发丝和衣物物理参数不属于开放通道。

语义值为 `0` 时对应模型默认值。正负方向通过通道映射配置确定；panda_cake 和 Hiyori 可以有不同映射方向，但协议本身不变。

## 七、数据流

### 7.1 用户即时指令

```text
用户点击发送
  → ImmediateGestureParser 同步解析原始文字
  → ParametricGestureGenerator 生成 MotionPlanV3
  → 下一渲染帧送入 Live2DStateMixer
  → 模型立即执行
  → 原聊天消息同时照常发送给后端
```

### 7.2 AI 回复动作

P0 已规定模型输出的第一行是 `EMOTION`、第二行是 `ACTION`。P1 不新增第三种文本控制头，避免破坏已经稳定的流式解复用器。

AI 在 `ACTION:` 后输出 v3 动作 JSON。后端根据是否存在 `tracks` 判断 v3；旧版 `intent` 结构继续按 v2 处理。

```text
AI 生成 ACTION v3
  → 现有流式控制前缀解复用器截获
  → MotionDirectorV3 校验
  → 用户级 WebSocket 发送 live2d_motion_v3
  → 前端按 motion_id 去重和检查有效期
  → Live2DStateMixer 接管合法通道
```

动作 JSON 不进入字幕、TTS、数据库和记忆，沿用 P0 的最终文本清洗边界。

## 八、状态混合和优先级

优先级按通道生效：

```text
安全限幅
  > TTS 口型专属控制
  > 用户即时指令
  > AI 上下文动作
  > 本地微反应
  > 待机动作
  > 模型默认值
```

规则：

- 用户执行点头时只占用 `head_pitch`，AI 仍可控制眼神、眉毛和身体；
- 嘴部参数只接受 TTS 口型层；
- 自动眨眼和眼睛表情使用受控组合，不通过最后写入互相覆盖；
- `override` 轨道按优先级取得通道所有权；
- `additive` 轨道在较低层基准上叠加，并在最后统一限幅；
- 同一来源的新动作替换旧动作时使用 100～180 毫秒交叉淡化；
- 用户新指令可以中断相同通道上的旧用户指令；
- 不同通道允许并发；
- 动作结束后按 `out_ms` 平滑回到下一个有效层；
- 模型切换时清空旧模型活动动作和去重缓存，重新建立能力表；
- 组件卸载时清理 ticker、计时器、动作队列和缓存。

## 九、即时指令冲突规则

- “点头并眨眼”：生成一个包含多个轨道的并行动作；
- “先点头两次，再摇头”：生成共享总时长、不同时间区间的顺序轨道；
- 同一句话对同一通道给出互相冲突的指令：不执行本地动作，交给 AI；
- 明确否定优先于动作关键词；
- 数量超过 5 次时，本地最多执行 5 次，避免长时间占用；
- 未给次数时，点头和摇头默认 1 次；
- 未给速度和幅度时使用自然、克制的默认值；
- 本地解析器只处理动作请求，不根据普通聊天内容猜测情绪。

## 十、AI 表演风格

AI 输出稀疏关键帧，前端负责平滑连续化。风格结合：

- 日常状态以小幅头部、眼神和身体变化为主；
- 情绪明确时允许更明显的动漫式动作；
- 高表现动作需要上下文支持，不能每句话都触发；
- 确定性随机只改变小范围细节，不改变语义和次数；
- AI 不需要知道当前模型参数 ID；
- AI 输出非法或缺失时，回复文本和语音仍必须正常完成。

## 十一、异常处理与防卡死

1. 每条轨道独立采样并捕获异常；
2. 所有外部数值进入混合器前执行 `Number.isFinite()`；
3. 输出值按真实参数范围限幅；
4. 缺少参数映射时跳过对应通道；
5. 动作超时后强制淡出；
6. 重复 `motion_id` 不重复播放；
7. 超过有效期的 WebSocket 动作直接丢弃；
8. 混合器整体异常时回退到“默认值、呼吸、眨眼和口型”的安全状态；
9. ticker 最外层继续保留 P0 的异常隔离，保证下一帧可以执行；
10. 开发环境记录拒绝原因，生产环境限制重复日志。

## 十二、性能要求

- 即时指令解析和曲线生成必须为同步纯函数，常规消息目标耗时小于 5 毫秒；
- 不新增一次 AI 请求；
- 单帧只采样当前活动动作；
- 活动动作结束后立即移除；
- 去重缓存采用有界容量和过期清理；
- 不在 ticker 中解析文本或重新构建模型能力表；
- 不因动作系统增加聊天首字等待时间。

## 十三、测试方案

### 13.1 前端单元测试

- 中文动作、次数、速度、幅度和方向解析；
- 否定句不触发；
- 并行动作和顺序动作；
- 参数化曲线的关键帧顺序、数量和范围；
- 相同随机种子结果稳定；
- 能力映射能够读取 ID、范围和默认值；
- 缺少私有字段或单个 API 异常时安全降级；
- 混合器优先级、叠加、覆盖、中断、淡出和超时；
- 嘴部保留通道不可被动作接管；
- 采样器异常后下一帧继续；
- v2 兼容路径继续工作。

### 13.2 后端单元测试

- v3 合法协议通过；
- 未知通道、嘴部通道、`NaN`、无穷值和乱序时间被拒绝；
- 超量轨道、关键帧和超长时长受限；
- 服务端生成唯一动作 ID 和时间；
- 动作限频和强度策略；
- v3 失败时不会污染正文；
- WebSocket 事件仍按当前用户隔离。

### 13.3 集成与回归

- 后端完整 pytest；
- 前端完整 Vitest；
- Vite 生产构建；
- P0 文本清洗、WebSocket、口型和 ticker 回归；
- 构建产物同步后校验前后端文件一致性。

## 十四、人工验收

1. 连续发送至少 10 轮普通对话，模型持续呼吸、眨眼和进行细微动作；
2. 发送“上下点头三次”，模型立即执行三次；
3. 发送“慢慢摇头两次并眨眼”，速度、次数和组合正确；
4. 发送“不要点头”，模型不执行点头；
5. 用户动作进行中收到 AI 回复，口型正常且动作不突跳；
6. panda_cake 与 Hiyori 均不出现参数错误或模型冻结；
7. WebSocket 重连后旧动作不重复播放；
8. 浏览器进入后台再返回后动作系统恢复；
9. HBuilderX 打包后的 Android APK 完成核心场景真机测试。

## 十五、完成标准

P1 代码完成必须同时满足：

- 即时动作、v3 动作、能力映射和状态混合器均已实现；
- 新增自动化测试全部通过；
- 原有后端和前端测试全部通过；
- 前端生产构建成功；
- 浏览器核心人工场景验证通过；
- `docs/功能清单.md` 按真实结果更新；
- 所有变更留在 `codex/p1-live2d-motion-v3` 分支；
- 未经用户明确要求不合并到 `main`。

Android APK 真机测试必须由实际设备确认。在确认前，功能清单中应保留为未验收，不得以桌面浏览器结果代替。
