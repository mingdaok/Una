# UNA 克隆语音精确口型同步与连续播放设计

> 日期：2026-07-31
>
> 状态：设计已确认，等待书面文档审阅
>
> 范围：P0，只优化 UNA 与 GPT-SoVITS 之间的语音生成、排队和播放链路

## 1. 背景与问题

当前 UNA 已能完成“流式文字回复 → GPT-SoVITS 合成 → Rhubarb 提取音素 → 前端播放音频并驱动 Live2D 口型”的完整链路，口型与语音在单个音频片段内基本同步。

当前体验问题主要有两类：

1. AI 的每个文字句段都独立发起一次完整 TTS 请求，并依次执行音频写盘、Rhubarb 分析和 MP3 转换，固定开销被重复支付。
2. 前端严格按 `chunk_index` 播放；当前一段播放结束而下一段尚未准备好时，播放队列会断粮，形成明显停顿。

GPT-SoVITS 默认还会在分段之间附加约 0.4 秒静音。UNA 已经在上游切分文字，却再次使用 GPT-SoVITS 的 `cut2` 进行内部切分，进一步放大了停顿和重复处理。

本次设计保留 Rhubarb 的精确时间轴，不采用仅按音量估算嘴型的方案。

## 2. 目标

本阶段需要实现：

- 用户发送消息后，第一段语音尽快开始播放。
- 多句话之间不再出现明显的固定停顿。
- 每个语音单元的 Live2D 嘴型继续与实际音频时间严格同步。
- 同一会话的语音严格按顺序生成和播放，不重叠、不乱序。
- 能从日志中区分 GPT-SoVITS、写盘、Rhubarb、转码、网络投递和前端排队分别耗时多少。
- 某一语音单元失败时可以安全降级或跳过，不阻塞整个会话。

## 3. 非目标

本阶段不做以下内容：

- 不改造 GPT-SoVITS 模型结构或重新训练声音模型。
- 不取消 Rhubarb，也不使用“声音响度直接控制嘴巴”的粗略口型。
- 不在第一阶段启用 GPT-SoVITS 真流式字节播放；真流式与精确音素时间轴的组合留作后续优化。
- 不调整 AI 大模型的回复内容和人格。
- 不处理群聊或多角色同时发声。

## 4. 方案选择

采用“短首段 + 后续合并 + 单会话有序预生成 + 完整音频精确口型”的方案。

没有选择逐字节真流式播放，是因为 Rhubarb 需要完整音频才能生成可靠的音素时间轴。若直接播放尚未完成的音频，要么嘴型滞后，要么只能退化为音量驱动，与“嘴型和语音同步”的核心要求冲突。

没有选择简单放大前端缓冲，是因为它会增加首句等待时间，而且不能消除 GPT-SoVITS 内部静音和重复请求开销。

## 5. 总体架构

语音链路划分为五个职责清晰的单元：

1. **文字聚合器**：接收 AI 流式文字句段，生成适合朗读的语音单元。
2. **会话语音调度器**：每个会话只维护一条有序生成队列，避免并发请求争用 GPT-SoVITS。
3. **语音生成器**：调用 GPT-SoVITS，写入临时音频，并执行 Rhubarb 与必要转码。
4. **WebSocket 投递层**：按语音单元顺序发送音频地址、音素时间轴和索引。
5. **前端播放队列**：预加载后续音频，按同一音频时钟启动声音和口型。

数据流如下：

```text
AI 流式文字
  → 文字聚合器
  → 会话有序生成队列
  → GPT-SoVITS 完整音频
  → Rhubarb 精确音素
  → WebSocket 有序投递
  → 前端预加载队列
  → 音频与口型共用播放起点
```

## 6. 文字聚合规则

### 6.1 第一语音单元

第一语音单元优先降低等待时间：

- 收到第一个语义完整、适合朗读的短句后立即入队。
- 不为了凑长度等待后续长文本。
- 纯控制帧、空白和不可朗读符号不得进入语音队列。

### 6.2 后续语音单元

后续文字允许在很短的聚合窗口内合并：

- 目标长度为 40～60 个中文字符。
- 默认聚合等待窗口为 200 毫秒。
- 遇到明显段落结束或文本流结束时立即封口，不继续等待。
- 单个语音单元以 80 个中文字符为硬上限，达到上限立即封口，防止单次 TTS 等待过久。

聚合器只决定“哪些文字属于一个语音单元”，不负责生成音频，也不直接操作 WebSocket。

## 7. GPT-SoVITS 请求策略

UNA 已经完成上游分段，因此短语音单元使用以下策略：

- `streaming_mode: false`：先保留完整音频，以便 Rhubarb 精确分析。
- `text_split_method: cut0`：短单元不再被 GPT-SoVITS 二次切分。
- `fragment_interval: 0.05`：把内部追加静音从默认约 0.4 秒降低到约 50 毫秒。
- 保留当前参考音频、参考文本、语言和声音速度配置。

当外部调用绕过聚合器并传入超过 80 个中文字符的文本时，受控回退到 `cut5` 标点切分，防止单次推理过长或模型异常。是否回退只由统一的请求构造函数决定，不能由多个调用点各自判断。

运行 GPT-SoVITS 时必须确认启动信息显示：

- `device: cuda`
- `is_half: true`
- `torch.cuda.is_available(): true`

若服务实际退回 CPU，本次调度优化仍能减少停顿，但无法达到预期生成速度，日志必须明确提示。

## 8. 单会话有序语音调度器

每个会话维护独立的语音作业队列，语音单元具有：

- 会话标识
- 回复标识
- 连续单调递增的语音单元索引
- 待朗读文本
- 创建时间
- 生成状态
- 音频和音素结果

同一会话的 GPT-SoVITS 生成任务按索引串行执行，下一单元可以在当前单元播放期间提前生成。不同会话是否并发由全局并发限制控制，避免显存被无限并发请求占满。

调度器必须保证：

- 不使用无序的“每句直接 `create_task`”作为最终投递顺序依据。
- 单元生成成功后只能按连续索引投递。
- 用户发起新一轮回复时，旧回复尚未投递的作业可按明确规则取消或标记过期。
- WebSocket 重连不会重复播放已确认消费的旧语音单元。
- 一个作业异常不会让队列永远卡在该索引。

## 9. 精确口型同步

每个语音单元继续先生成完整音频，再由 Rhubarb 生成相对于该音频起点的音素时间轴。

前端播放时：

1. 音频解码和音素数据都准备完成后，记录统一的播放起点。
2. 使用 `AudioContext.currentTime` 作为口型采样时钟。
3. 当前音素位置按“当前音频时钟减去该单元播放起点”计算。
4. 暂停、恢复、播放失败和切换音频时同时更新声音状态与口型状态。
5. 音频结束或异常中止时，嘴部参数平滑回到闭合默认值。

Live2D 动作层不得覆盖嘴部通道；已有“口型最后写入”的优先级继续保留。

## 10. 前端连续播放策略

前端仍按索引消费音频，但新增明确的准备状态：

- `received`：已收到元数据。
- `loading`：正在预加载或解码。
- `ready`：音频和音素均可播放。
- `playing`：当前正在播放。
- `done` / `failed`：已结束或安全跳过。

当前语音播放期间主动预加载下一单元。当前单元结束后：

- 下一单元已 `ready`：立即衔接播放。
- 下一单元仍在生成或加载：记录一次“队列断粮”及等待时长，准备完成后继续。
- 下一单元失败：安全跳过并继续后续索引。

不通过在每句话之间人工插入静音解决衔接问题。

## 11. 结束语义

现有文字流结束不再等同于语音播放链路结束。

需要区分：

- **文字生成结束**：AI 不再产生新文字。
- **语音作业封口**：聚合器不再产生新语音单元。
- **语音生成结束**：所有语音单元均已成功或失败终止。
- **前端播放结束**：所有已投递语音单元均已播放或跳过。

`audio_stream_end` 必须表达语音生成队列已经封口且所有单元均已得到终态，不能在仅完成 LLM 文字输出时提前发送。

## 12. 性能日志与可观测性

每个语音单元使用同一个 `reply_id + chunk_index` 串联日志，至少记录：

- 聚合等待耗时
- 调度队列等待耗时
- GPT-SoVITS HTTP 请求耗时
- 音频写盘耗时
- Rhubarb 分析耗时
- WAV/MP3 转换耗时
- WebSocket 投递耗时
- 前端从收到到 `ready` 的耗时
- 前端等待前一单元结束的耗时
- 队列断粮等待耗时
- 实际播放开始和结束时间

日志不得输出访问令牌、媒体票据或完整敏感 URL。

## 13. 失败与降级

- GPT-SoVITS 不可用时，沿用 Edge TTS 降级，但仍进入相同的 Rhubarb、索引和播放队列。
- Rhubarb 失败时，不阻止音频播放；该单元使用安全的轻量口型降级，并在结束时复位嘴部。
- 转码失败时，若浏览器可播放现有格式则使用原格式，否则把该单元标记失败并继续队列。
- WebSocket 已断开时不继续向旧连接投递；重连后的新连接代次不得消费旧连接回调。
- 所有临时文件均按现有媒体生命周期清理，不能因取消任务长期残留。

## 14. 测试设计

### 14.1 后端自动化测试

- 短单元请求使用 `cut0` 和 `fragment_interval=0.05`。
- 超过阈值时正确回退长文本切分策略。
- 第一短句立即封口，后续句段按窗口和长度聚合。
- 同一会话即使生成耗时不同也按索引投递。
- 单元失败后后续单元仍可继续。
- 新回复能使旧的待投递作业失效。
- `audio_stream_end` 不早于所有语音作业终态。
- 日志不泄露 ticket 或令牌。

### 14.2 前端自动化测试

- 音频与音素使用同一播放起点。
- 下一单元已准备时无额外人工延迟。
- 下一单元未准备时记录断粮并在准备后继续。
- 加载失败、播放失败和 WebSocket 重连不会卡死队列。
- 音频结束、跳过或异常时嘴部恢复默认值。
- Live2D 普通动作不能覆盖 TTS 嘴部通道。

### 14.3 人工验收

使用同一段至少包含 4 个短句的回复进行测试：

1. 第一段语音能较快开始。
2. 句子之间没有明显的约 0.4 秒固定静音。
3. 连续播放过程中没有重叠、乱序或重复。
4. 嘴巴张合与听到的音节一致，不提前、不明显滞后。
5. GPT-SoVITS 故意停止后可降级播放，队列不会永久卡住。
6. 连续对话 10 轮后，Live2D、文字、音频和 WebSocket 均保持工作。

## 15. 验收指标

本阶段以用户可感知体验和可诊断数据共同验收：

- 消除由默认 `fragment_interval=0.4` 引起的固定长静音。
- 在当前本机 CUDA 环境和正常网络条件下，从第一语音单元封口到可播放的目标耗时不超过 2.5 秒。
- 在包含至少 4 个语音单元的回复中，相邻单元播放间隔中位数不超过 150 毫秒，P95 不超过 300 毫秒；Edge TTS 降级和外部服务故障场景单独统计。
- 若仍发生断粮，日志能够明确显示瓶颈属于生成、Rhubarb、转码、网络还是前端加载。
- 所有自动化测试通过，并完成桌面浏览器人工验收。
- Android APK 验收单独保留为待办，桌面结果不替代真机结果。

## 16. 分阶段实施边界

本设计对应一个可独立交付的 P0：

1. 请求参数去除二次切分和长静音。
2. 后端文字聚合与单会话有序语音调度。
3. 完整音频 + Rhubarb 精确口型。
4. 前端预加载、连续消费和断粮统计。
5. 全链路阶段耗时日志、自动化测试和人工验收。

只有当以上方案仍无法满足首段延迟目标时，才进入下一阶段研究“GPT-SoVITS 真流式音频 + 增量或延迟校正口型”。该后续研究不属于本次实施范围。
