## 4. 详细问题与修改方案

### F01：发送锁之后缺少最后一次权限检查

位置：`service.py:265` 的 `deliver()`、`adapter.py` 的 `action()`；相关撤销逻辑在 `store.py:240` 和群设置方法。

`deliver()` 验证权限后，把 Outbox 改为 `sending`，随后 `action()` 才等待 `send_lock`。等待期间群设置可以变化，绑定也可以解绑。拿到锁以后没有重新检查业务权限，`preferences()` 也不取消 `sending` 项。

复现：人工占住模拟传输锁 → 启动投递 → 看到 `sending` → 关闭群 → 释放锁。仍捕获到 `send_group_msg`。这条消息在关闭群时尚未交给协议端，与“已经发出无法撤回”不同。

修改方案：

- 将“准备发送”和“已向协议端提交”分开记录，定义明确的交付边界。
- 取得传输锁后、调用 `send_json()` 之前，重新检查会话代次、绑定/群设置版本、任务状态、素材版本和有效期；业务检查通过回调或发送意图对象注入，避免适配器直接依赖数据库模块。
- 撤销操作取消未提交项。已提交但回执未到仍为 `unknown`，不得重发。对异步提交瞬间的竞争明确语义，不能承诺撤回已提交消息。
- 发送锁等待设置超时，不让背压无限占住 `sending`。

验收：在获取锁前撤销绑定、禁用群、禁用素材，模拟套接字收到的发送动作必须为零；已经提交后断线仍只产生一次发送。

### F02：机器人自身撤回事件没有关联 Outbox

位置：`social_runtime.py:359` 的 `recall()`、`store.py:570` 的 `delivered()`。

机器人候选消息通常没有 `qq_messages.platform_id`，真实消息 ID 存在 `qq_outbox.platform_id`。撤回处理只用前者匹配，因此收到机器人自己消息的撤回通知后，候选消息依然 `delivered=1`，还能被历史和引用索引读取。

复现结果：发送回执 ID 为 `900`，收到该 ID 的群撤回事件后，机器人历史的 `delivered` 仍为 `1`。

修改方案：通过本群、本机器人、当前代次的 Outbox 映射定位交付片段，标记该片段撤回，再重建有效历史。多段消息只移除撤回片段，不能误删其他已交付片段。清理相关引用索引，并取消依赖被撤回内容的未提交计划。

验收：文字、图片、语音以及第二段文字的撤回均生效；另一群相同消息 ID 不受影响；撤回发生在生成/等待发送期间也不继续使用撤回内容。

### F03：时间来源丢失，旧消息可能重新获得发送期限

位置：`adapter.py` 的 `normalize()`、`store.py:306` 的 `ingest()`、`service.py:190` 的 `run()`、`store.py:526` 的 `_out()`。

普通事件未保留 OneBot 的 `time`，入库时间使用当前时间。群自主 TTL 因此无法识别协议端刚重放的旧消息。私聊与直接提问恢复时也没有统一的请求过期判断，生成完再分配新的发送期限。

复现：向模拟接收端提交 `time` 为两天前的直接群消息，仍生成 1 个待发送回复。历史补取另有时间检查，不能覆盖普通事件重放路径。

修改方案：分别保存 `event_time`、`received_at`、`source` 和 `expires_at`。新事件时间过旧、明显未来或无效时进入明确的过期/异常策略，不冒充新消息；兼容协议缺失时间时使用接收时间但标注。恢复任务沿用原始截止时间，不因重启或重新生成延长。私聊允许的积压时长需要写入配置和文档。

验收：两天前消息、重启后的过期私聊、历史补取均不会误触发新回复；正常轻微时钟偏差不误杀。

### F04：补取自己的已发送消息会重复入库

位置：`social_runtime.py:330` 的 `history()`、`store.py` 的 Inbox 去重和候选消息落库。

入站去重只查 Inbox；机器人在线发送时没有对应的入站 Inbox。补取拿到这条已发送记录时，会另建一条消息，再改成 assistant，从而与原候选历史重复。

复现：本地已确认一次机器人回复，补取包含该平台 ID 的记录后，assistant 消息数由 1 变为 2。

修改方案：建立按 `(bot, conversation, platform_message_id)` 的平台消息映射。补取先匹配已有交付片段；匹配后只补充平台时间/元信息，不新增历史。新历史消息使用幂等 upsert；多段发送不能合并错位。

验收：连续补取、重连再补取、包含多段机器人回复的补取，模型上下文每个真实片段只出现一次。

### F05：已复核计划没有检查完整的新消息水位

位置：`social_runtime.py:177` 的 `fresh()`。

查询只取触发消息后的前 20 条；首次复核另查全部 ID，但 `rechecked=1` 后直接只对前 20 条判断。因此第一段发出后又到第 21 条新消息，后续片段可能继续使用已经过时的许可。此外，复核传入的是原触发文本，不一定是规划器最终选择的回复目标。

复现：先加入 20 条同话题消息并通过复核，再加入第 21 条换话题消息，第二次 `fresh()` 仍返回 `True`。

修改方案：每个会话维护单调递增的消息水位。记录复核时的水位与目标 ID，发送每个片段前比较最新水位；发生变化保守取消或按一次复核预算重新判断。复核内容使用实际目标及计划依赖，不用触发文本代替。

验收：第 21 条、第 100 条新消息、较早目标、多段回复与并发撤回都能正确过期；复核次数有界。

### F06：诊断把失败当作正常提问

位置：`social_runtime.py:121` 的异常处理及生成末尾 `decision_log()`；`social_api.py:69` 的诊断接口。

直接提问生成失败时会发送固定失败提示，但仍记 `direct_question`；自主失败只保留 `generation_failed`，没有模型 HTTP 状态、格式校验字段、阶段等可排查信息。界面显示“直接提问”不能证明模型生成成功，这解释了此前排错时信息不足的问题。

复现：模拟模型抛出格式异常，最终诊断仍为 `direct_question`。

修改方案：拆分 `trigger_type`、`decision`、`generation_status`、`delivery_status`，记录阶段、异常类型、HTTP 状态、校验字段路径及关联任务 ID。只记录经过清洗的错误码，不保存密钥、完整 HTTP 错误体、签名媒体 URL 或用户全文。将空响应、超时、JSON 非法、Schema 非法、权限取消分别显示。

验收：模拟 401、429、超时、空内容和非法 JSON，管理员能看懂原因；日志中不出现测试密钥和私人输入；普通用户看不到他人的错误细节。

### F07：素材 SHA 去重不在同一个事务中

位置：`stickers.py:47` 的 `add()`、`social_api.py:107` 的上传接口。

先查询是否存在，再开始插入事务。上传和后台收集可在不同线程同时查到“不存在”，最终一个插入触发唯一约束。上传只捕获 `MediaError`，可能直接返回 500。

复现：让两个线程同时通过相同 SHA/作用域的检查，结果为 `['IntegrityError', 'ok']`。

修改方案：事务中再次查询或使用 `INSERT ... ON CONFLICT DO NOTHING`，再获取已有 ID。物理文件使用临时文件加原子替换，文件写入与数据库提交失败有补偿；已有 rejected 墓碑不能被这条路径重新激活。

验收：并发上传/收集同图均返回同一素材 ID，数据库只有一条有效记录，不产生 500、损坏文件或自动复活。

### F08：预览只校验文件，不校验删除状态

位置：`social_api.py:153` 的 `preview()`、`stickers.py:90` 的 `remove()`。

相同 SHA 跨群共用一个物理文件。删除某群素材只打墓碑，若另一群仍用它就保留文件。预览端点没有检查 `status='rejected'`，因此拿着旧素材 ID 的管理员仍能取图。这不是未登录访问漏洞，但违反了“删除后不可访问该素材”的语义。

复现：同图分别加入两群，删除其中一个，被删除记录的 `library.path()` 仍能读取。预览接口正是使用该读取路径。

修改方案：预览同时验证授权作用域、素材状态和文件状态，rejected 返回 404/410。根据产品定义区分管理员预览 disabled 与彻底删除；墓碑状态禁止直接 PATCH 为 ready。保留其他作用域仍在使用的物理文件。

验收：被删除 ID 的认证预览也失败，另一群有效 ID 正常；无权用户始终不能预览。

### F09：数据库读取也申请写锁，并同步运行在异步主循环

位置：`store.py:139` 的 `db()`/`rows()`；`service.py` 接收、调度、投递路径；`social_store.py:80` 与 `store.py:416` 的历史构建。

所有读取都执行 `BEGIN IMMEDIATE`，SQLite 忙等待最长 10 秒。后台素材线程、主应用写入或清理占锁时，主事件循环可能被同步数据库调用阻塞，连带延迟 WebSocket 心跳和回执。历史构建还会为每条 assistant 记录单独查询 Outbox，相关检索最多读取 1000 条，形成大量重复查询。

修改方案：拆分只读连接和短写事务；评估并启用 WAL；把数据库工作放到受控执行器/独立存储队列，不在事件循环中同步忙等。批量加载交付映射，消除每条历史一次查询。保留单 worker 约束，不能简单取消事务来换速度。

验收：模拟写锁占用、多个群消息和后台上传并行，事件循环心跳仍可运行；报告查询次数、等待时间和回执延迟。千人身份测试不等于千人吞吐测试。

### F10：历史导出队列可能被永久跳过的项目占满

位置：`service.py:369` 的 `postprocess()` 导出查询与 `store.py:101` 的 `export_history()`。

查询先拿最多 20 个未导出的私聊 Outbox，之后才检查绑定版本和 `share_history`。不允许导出的项目既没有被查询排除，也没有标记已跳过；因此最前面的 20 项可能反复被选中，后续真正允许导出的会话一直到不了。

修改方案：把当前有效绑定版本、会话代次和共享权限下推到查询，按 Inbox 去重分页；对终态项目显式标记原因。明确“后来打开共享”是否追溯旧消息，不能由队列偶然顺序决定。

验收：先放 20 项不共享或已撤销的记录，再放一项可导出记录，后者仍能在一个处理周期内完成；禁止导出的内容不进入网页历史。

### F11：后台工作有队首阻塞和预算缺口

位置：`social_runtime.py:223` 的 `work_once()`、`:287` 的 `tts()`；`social_api.py` 上传/重建；`service.py:190` 的维护调度。

- TTS 总取最早 pending 项；其正文未交付时重新置为 pending，下一次仍取它，后面的可执行语音被挡住直到前项交付或过期。
- 索引、素材描述、收集、历史补取共用一个串行媒体队列；大量慢描述会拖延手动历史补取。
- 只有自动收集路径有数量/日预算；管理员上传描述和反复重建没有统一入队上限和去重活跃任务策略。
- `notifications()` 在主调度循环中执行并逐用户等待生活来源，用户多时影响聊天调度。

修改方案：增加 `ready_at/depends_on/priority`；查询只取依赖已满足的任务，待正文任务不占队首。统一各入口的队列容量与模型调用预算，按 kind 公平调度；通知扫描放独立任务。保留 TTS 推理占用约束，不用无限并发解决。

验收：队首文本未发时，后续已满足条件的 TTS 能执行；收集/索引压力不饿死历史补取和聊天；重复点击重建只有一项活跃任务。

### F12：嵌入服务降级不可见、不可恢复

位置：`stickers.py:113` 的 `vector()`、`:135` 的 `index()`。

任意一次超过 2 秒就把 `self.embed=None`，本进程以后都不再尝试。后台 `index()` 即使写入 NULL 向量，任务仍标为 done。模型冷启动或瞬时繁忙后，管理员可能一直以为在语义检索，实际只剩文字匹配。

修改方案：设置独立的冷启动/常规预算与熔断恢复时间；区分“文字索引可用”“语义索引成功”“语义索引降级”。保存明确模型标识、版本和维度；降级可手动重试，不在每次聊天反复启动失败模型，不重新下载现有模型。

验收：首次慢、后续恢复、模型切换、后台繁忙均有可见状态；超时线程未结束前不叠加新推理。

### F13：QQ 关闭也有数据库副作用

位置：`main_server.py:281` 的无条件 `ChannelStore(...)`，`service.py:168` 的 `start()` 和 `close()`。

功能关闭时仍创建 QQ 服务、执行表迁移和素材目录初始化。`close()` 无论是否取得 worker lease 都会运行 `recover()`。迁移发生在单 worker 租约之前。若另一个进程误用同一库，关闭实例也可能影响活动 QQ 任务状态。

修改方案：只有启用且配置有效时才初始化可写运行时；状态接口使用不写库的 disabled 状态对象。取得单实例权限后再迁移/恢复，记录 `started/lease_owned`，仅拥有租约的实例执行关闭恢复。迁移和备份使用显式关闭的 SQLite 连接。

验收：功能关闭时启动/关闭服务器不新增 QQ 表、不改变任务状态；第二实例被拒绝时不先修改库；升级前备份仍有效。

### F14：裁剪会丢弃当前消息，规划结果也没有全部被使用

位置：`conversation_service.py:113` 的 `bounded_history()` 和 `decide()`；`social_runtime.py:31` 的 `generate()`。

裁剪按整个 JSON 记录能否放进 6000 UTF-8 字节决定是否保留。当前 2000 个中文字符加身份字段就超过预算，规划器可能完全看不到当前消息。`Decision.context_message_ids` 与 `preferred_mode` 被校验后也未实际参与后续上下文/表达方式构造。

复现：仅传入一条正文为 2000 个中文字的群消息，`bounded_history()` 返回空列表。

修改方案：优先保留当前目标、身份字段和关键引用，超长正文局部截断并明确标记，再裁剪低相关旧消息。以实际传给模型的可见 ID 校验计划。将规划器选择的上下文和表达方式落实到 ReplyPlan 构建，或删除无效字段，避免两阶段各自重新猜。

验收：长文本、长昵称、长引用都不能清空当前目标；对象身份保留；不可见 ID 被拒绝；规划为纯表情时不会无故丢弃意图。

### F15：私聊语音失败没有合适的查看入口

位置：`social_api.py:161` 的 `media_jobs()`、QQSocialAdmin 的后台任务页。

任务列表只取群任务和无会话任务。私聊 TTS 在后台合成失败时没有生成 audio Outbox，既不出现在这个列表，也不出现在仅查询失败 Outbox 的“发送异常”区域，用户只看到文字、无法判断语音为何没到。

修改方案：普通用户仅能查询自己的媒体任务状态；管理员可查看脱敏的全局健康汇总，查看私人内容仍应受到归属限制。任务列表显示目标、类型、状态、阶段和时间，分别区分合成失败、未提交、回执不明。

验收：用户 A 能查看自己的失败语音，不能读取用户 B 的任务；不额外暴露文本、QQ 全号、本地路径或下载 URL。

## 5. 额外风险与改进建议

### R01：音频解码仍需限制容器/解复用器（优先验证）

`media.py` 对输入只做下载大小和 ffprobe 时长检查，FFmpeg 自动探测格式，允许 `file,pipe`。这能阻止网络协议，却不能单凭这一项证明输入容器不会引用其他本地文件。

本轮只用临时生成的静音 WAV 和临时 HLS 播放列表验证：当前 ffprobe 能接受引用临时本地 WAV 的列表并返回时长；当前 PATH 下的 ffmpeg 因 Windows 路径解释不同而转码失败。**尚未证明完整识别链路可窃取任意本地文件，不应把它写成已成功利用的漏洞。** 同时发现 ffprobe 与 ffmpeg 的表现不一致，应确认是否来自同一安装版本。

方案：固定部署二进制，预检实际音频容器/编码，使用经验证的解复用器白名单，拒绝 HLS、concat、播放列表等引用型输入；必要时使用隔离目录和受限子进程。加一个“上传容器不能读取临时目录之外的测试文件”的负向测试。不能通过放开网络/文件协议解决格式兼容问题。

### R02：95% 测试模式需要更明确的范围和退出机制

当前测试开关是全局环境变量，对启用的白名单群生效，没有到期时间；它跳过模型的发言判断，但仍经过总配额与话题有效性检查，因此 95% 是“符合调度条件的一轮尝试概率”，不是每条消息 95% 送达。

建议未来增加按群启用、开始时间、显式到期时间和剩余时长提示，恢复普通模式时使旧测试计划失效。测试模式也不应跳过用户明确要求停止、被禁言等硬规则。**本轮保留用户已要求的 95% 设置，不擅自关闭。**
